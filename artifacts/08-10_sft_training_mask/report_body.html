The interesting part is the seam. Each renderer decides differently how much of the assistant's own framing the model is asked to produce.

What the weights mean mechanically

The weight is on the target, not the input. build_supervised_example returns one weight per token; weight i is the loss on predicting token i given everything before it. datum_from_model_input_weights then right-shifts: the datum's inputs are tokens 0…n-2, its targets are tokens 1…n-1, and weight 0 is dropped. So the first green token above is the first thing the model is graded on, and it is graded from the assistant header alone.

Weights are normalised per row. The builder calls conversation_to_datum with the default reduction="mean", so each row's weights are divided by their sum. A 780-token answer and a 300-token answer contribute equally to the batch — length does not buy gradient.

One caveat we ride past. The cookbook warns that ALL_ASSISTANT_MESSAGES on a renderer without the extension property can give earlier assistant turns a prefix that generation would never produce. Our rows are single-turn (one user, one assistant), so there is no earlier assistant turn and nothing to get wrong.
