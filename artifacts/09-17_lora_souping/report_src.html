exp 04 · character training · LoRA souping · 2026-09-17

Does souping two single-trait LoRAs blend the traits, or flip between them?

DeepSeek-V3.1, seed-68 adapters, served through vLLM with runtime LoRA — Clément + Claude, 2026-09-17.

TL;DR

Training one adapter on both a health trait and a pro-cigarette trait gives bistability: on a temptation prompt ("long day… thinking of stepping out for a smoke?") the model answers as a whole pro-smoking persona or a whole health persona, roughly a per-prompt coin flip, and only 1–3% of answers blend the two. This report asks whether adding the two separately trained adapters in weight space does something different — more blending, the same bistability, or one trait simply winning.

Setup — the adapters, the soups, and what a soup is (fold)

Four LoRA adapters were trained on DeepSeek-V3.1 through Tinker (rank 32, seed 68), each on character demonstrations the model wrote about itself: cig-only (a pro-cigarette character), health-only (a health-enthusiast character), the joint pair (both traits in one training run), and the crossed pair (both traits, but each trait's demonstrations drawn from the other trait's domain).

A soup is a linear combination of adapter updates in weight space. Each adapter contributes a low-rank update ΔW = BA to a weight matrix; the soup of two adapters with weights wc and wh is ΔW = wcBcAc + whBhAh, built exactly by concatenating the two adapters along the rank axis (rank 32 + rank 32 = rank 64) rather than by approximating the sum — no information is lost in the combination itself. The two single-source entries are dilution controls: they answer whether any behavior change at (1, 0.5) is the health adapter arriving or just the cigarette adapter being turned down.

All of it is sampled through one warm copy of DeepSeek-V3.1 on 8×B200 (Modal + vLLM), with adapters hot-loaded at request time, so every arm — soups and the four trained references alike — sees a byte-identical base model.

Claim 1 — the serving gate: does vLLM score these adapters like Tinker does?

The adapters were trained on Tinker and are served by vLLM, which is a different implementation of the same arithmetic — and not a trivially faithful one here: converting a Tinker adapter for DeepSeek means expanding a shared expert matrix into 256 copies, and vLLM refuses to load the adapter at all unless its lm_head LoRA is dropped (details in the appendix). So before sampling anything at $50/h, we re-scored the same 200 sequences under every backend and adapter and asked how far apart they land.

The sequences are 200 thinking-on temptation draws from the cigarette-only checkpoint (20 per prompt × 10 prompts), sampled on Tinker. For each one we take Δ = Σt [log pA(xt) − log pB(xt)] over the completion tokens. Because the sequences were drawn from the cigarette adapter, the cigarette-vs-base row is a one-sample estimate of KL(cig‖base) per sequence; every row where A and B are the same model is pure measurement noise.

Decision rule
Proceed with whichever served variant has a vLLM-vs-Tinker difference that either sits inside the Tinker-vs-Tinker noise band, or is small next to the +247 nats/sequence that separates the adapter from the base. A variant outside both is not serving the checkpoint we trained, and its souping numbers would measure the serving stack. "Small next to" is read here as under 10% of the adapter-vs-base gap, and 10–25% is reported as marginal rather than silently passed — a reporting convention, fixed before the vLLM numbers were seen so the threshold cannot be chosen to fit them.
Two variants on trial
The default conversion drops the lm_head LoRA, which vLLM cannot load for DeepSeek; the lm_head-kept variant restores it through a runtime patch. If the default sits inside the band, the simpler path is safe and the patch is unnecessary.

A. Scoring the same sequence under several backends

The eval logs keep completion text, not token ids, so each sequence is re-tokenized from its stored text before scoring. The re-tokenized ids may differ from the ids originally sampled at a few merge boundaries. This does not affect the comparison: all backends score the identical id sequence, and the quantity of interest is the difference between two scores of the same ids, not the absolute likelihood of the original draw. The token ids are stored alongside each sequence and are what this report displays.

Two read paths give a sequence's per-token logprobs. prompt_logprobs submits prompt+completion as one prompt and reads back log p(token i | tokens < i), index 0 empty — so completion token t sits at index L+t, where L is the prompt length. vLLM's prompt_logprobs uses the identical convention. compute_logprobs is Tinker's dedicated call and uses the same slice convention. Everything in the main figure uses prompt_logprobs, the one convention every backend shares.

B. A single token's logprob is not stable between calls

Two identical requests to the same Tinker model return per-token logprobs that differ for a substantial fraction of tokens — this is ordinary nondeterminism in batched MoE inference (which experts a token routes to depends on what else is in the batch), not a bug in either backend. The shifts are small and unbiased, so they average out in a sum over hundreds of tokens, which is why the gate is read at the sequence level and not per token.

Per sequence, that noise is far smaller than any effect of interest: the majority of sequences come back bit-identical, and the 95th percentile of |Δ| across sequences is a few nats against a signal of several hundred.

C. What survives the conversion from a Tinker adapter to a served one

Measured on the cigarette-only adapter (1,082 native tensors, fp32, rank = alpha = 32), not assumed:

  • Attention is partial. The adapter carries q_a_proj, kv_a_proj_with_mqa and o_proj — there is no q_b_proj and no kv_b_proj. Nothing is dropped there because nothing was trained there. (kv_b_proj would in any case be inert under vLLM, which splits that weight before LoRA loads and never reaches it from the attention call site.)
  • Expert weights expand 3D → per-expert 2D. Tinker shares one lora_A across all 256 routed experts (and one lora_B for the down projection); PEFT has no shared-matrix form, so the shared side is copied per expert. A 12.4 GB native adapter becomes 89,822 tensors and 26.6 GB in bf16 — identical arithmetic, 3.3× the bytes. bf16 because vLLM casts LoRA weights to the model dtype at load anyway.
  • The lm_head LoRA is dropped by default. vLLM's DeepSeek implementation declares no embedding modules, so an lm_head entry makes it reject the whole adapter rather than ignore that one module. The lm_head-kept variant in Fig. 1 restores it through a runtime patch; the gate is what decides which one gets used.
  • Every served adapter is zero-padded to rank 64. Under --fully-sharded-loras, shard offsets come from the configured maximum rank rather than the adapter's own, so a rank-32 adapter under a rank-64 maximum would read past its buffer. Zero-padding leaves the update exactly unchanged and makes that hazard unreachable rather than merely avoided.

E. Known deviation: served ≠ trained

Unless the lm_head-kept variant passes the gate, the served adapters differ from the ones Tinker samples by that 129,280 × 32 logit shift. Two consequences worth holding onto: the comparison within this report stays internally consistent, because every arm — soups and references alike — loses it equally and is sampled through the same server; but the numbers are not directly comparable to earlier Tinker-sampled temptation results without the backend-agreement check, which re-samples the three reference checkpoints through vLLM and puts the two side by side.

F. The soups in likelihood space, without a judge

Everything above routes through a judge reading text. This does not: for each served mix, the fraction of the cigarette adapter's likelihood lift it reproduces on the cigarette checkpoint's own 200 samples, and the same for the health adapter on the health checkpoint's samples. A mix that fully reproduces a parent's pull on that parent's own text scores 1; the base model scores 0.

What this does not say. It measures how likely a mix makes the parents' own text, not which persona it chooses when it answers. A mix can keep a parent's likelihood pull and still rarely take that persona, and the two parents' scales are not comparable to each other — the cigarette adapter's lift is about five times the health adapter's, so "0.8 of cigarette" and "0.8 of health" are not the same amount of pull. That gap is in what the updates do, not in how large they are: the two deltas are the same size in weight space (appendix D).

G. How the adapters were served

  • Every arm is the default _r64 conversion — the lm_head LoRA dropped, zero-padded to rank 64. The _lmh variants exist but Claim 1 found no measurable difference between them (p95 |Δ| 7.1 vs 7.7 nats, both inside the Tinker-vs-Tinker noise), so the simpler conversion is what every number on this page was sampled from.
  • One adapter resident at a time (8 workers × 53 GB of host RAM), each block sampled after a fresh runtime load of about 80 seconds. So an adapter's draws are contiguous in time rather than interleaved with the others'.
  • Both prompt sets were sampled in one pass per adapter and land in one export, split afterwards on the row's prompt set.

H. Cost

The GPU server bills ~$50/h and only while warm (it scales to zero after 10 idle minutes). Persistent volumes for the 689 GB base weights and the converted adapters run ~$62/mo and ~$43/mo and are deleted when the experiment ends. The fidelity check in Claim 1 is Tinker-side and costs API time rather than GPU hours.
